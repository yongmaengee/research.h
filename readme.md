# 하네스깎기..

### pain point
1. 참고해야하는 선행연구가 너무 많고 최근 학회로 올라오는 논문도 지속적으로 올라오기때문에 방법이 겹치는걸 검증하기 어렵지만 장점으로는 금방금방 비슷한 문제인식의 돌파 영감을 받을 수 있음.
2. 없는걸 만들어야하고 새로운 시도와 기존에 없는 해석을 만들어야하는게 본질적인 작업인데 매우 보수적으로 시도함. 검증이 안된 시도에 대해서는 너무 휴리스틱하게 시도. 과감함이나 야심찬 작업을 반려하거나 편향을 가지고 시도함.
3. 검증을 너무 과하게함. 간단한 직관으로도 알 수 있는 방법에 대해서 꼭 시드별로 검증을 하는 과정이나 취약점 파악이 너무 과하게 있음. 대부분의 논문이 limitation을 안놓는 경우도 있고 솔직하게 언급하지만 매우 작게 언급하거나 모든 검증을 다 해놓고 선보이지않음. 특히 AI분야는 학회논문투고위주라 저널급의 엄밀함을 자꾸 작은 실험에서 계속 따짐. 병목의 주요 원인이며, 방법을 찾는 과정에서는 성능향상 말고는 검증을 과하게 할 필요없고 눈에 띄고 주장할만한 결과가 나왔을때 방법을 검증하는것이 맞음(하지만 선행연구와 기여가 겹치는건 다른문제. 이건 빠르게 검증하거나 사전부터 알고있어야함.)
4. 문서관리와 코드작성 및 정리를 한번에 하다보면 내 지시사항이나 생각보다 llm의 출력이 컨텍스트를 더 많이 차지하는 경우, 사람이 알아들을 수 있는 텍스트가 아닌 형태가 되는 경우가 많음. 특히 한국어를 못하고 영어 유머를 한국어로 강제로 바꿔서 말이 안되는 상황이 많이 발생함. 따라서 오케스트레이터는 코드를 필요할때만 보고 kpi와 설명만을 읽고 정리하거나 답변하는것이 나을것이라 생각함.
5. 치명적인 문제로 본질적인 해결이 아닌 우회로 해결하여 가려진 상태의 국소적인 기여 주장을 자연스럽게 함. 시작부터 잘못된 문제에 대해서 잘못 넘어가서 치명적인 시작상황에서 이후 내용에도 지속적으로 전이됨. 
6. 5에 대해 사용자에게 유리하게 우회해서 결론을 내린걸 자기평가하기위해 검증을 강하게하는데 검증을 잘못된 핀트에서 강하게하고 우회해서 결론을 내리는건 정작 막지못하여 아무 하네스가 없는 상태보다도 생산성이 떨어짐. 따라서 모델별 분업이 더 나을것이라고 생각함.
7. 자꾸 본질적인 목표와 해결할 문제를 잊고 주객전도됨. 본질을 잘 염두해두고있다면 과도한 검증이 필요한지도 알아서 저울질을 할 수 있을것이라 생각함.
